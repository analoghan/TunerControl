VE Table Tuning Tool — Help

This tool analyzes MoTeC log data against your current VE table to compute per-cell corrections that bring your actual air/fuel ratio in line with your targets.

Quick Start

  1. Export a log from MoTeC i2 as CSV, or use the raw .ld file directly.
  2. Choose the tune the log was recorded with: a stored tune (suggested from the log) or its .m1pkg file.
  3. Click Process.
  4. Review the correction table — positive values mean "add fuel," negative means "remove fuel."
  5. Download the VE_New_Values.csv and import it back into M1 Tune.

Input Files

MoTeC Log File (.csv or .ld)

The tool accepts either a CSV export from MoTeC i2 or a raw .ld binary log file. Required channels:

  • Engine Speed — RPM for binning into the VE table columns
  • Inlet Manifold Pressure — MAP (kPa) for binning into VE table rows
  • Exhaust Lambda Bank 1 / Bank 2 — actual measured lambda (or "Exhaust Lambda" as fallback)
  • Fuel Mixture Aim — target lambda the ECU is commanding

Optional channels (used if present):

  • Fuel Closed Loop Control Bank 1/2 Trim — closed-loop trim already applied by the ECU
  • Coolant Temperature — for the coolant temperature filter
  • Throttle Position — for the TPS rate-of-change filter

Tune (.m1pkg)

The VE table is Engine Efficiency Main, read from the tune — a stored tune or an M1 Tune package (.m1pkg). The line under the tune controls shows which tune and table size were read. Use the tune that was in the ECU when the log was recorded, so the corrections apply to the values that were actually running.

The tool works on a single RPM × manifold-pressure table; a tune whose Engine Efficiency Main has more than one Ambient Pressure slice is refused. VE_New_Values.csv is an M1 v2 CSV, ready to import into M1 Tune.

Stored tunes

Tunes imported in the M1 Config Viewer appear in Or a stored tune. When you choose a log, the tool suggests the tune that was most likely in the ECU when it was recorded — the latest tune from the same ECU saved before the log started — and says why (or why none fits). Picking a .m1pkg or another tune yourself always takes precedence.

Filter Settings

Min Hit Count (default: 50)

A cell must have more than this many valid samples to produce a correction. Cells below this threshold are greyed out and left unchanged in the output. Higher values give more statistical confidence but require more log data.

Tip: For a first pass with limited data, try 20–30. For a final tune, use 50–100+.

Min Coolant Temp (default: 55°C)

Discards all samples where coolant temperature is below this value. This ensures you're only analyzing data from a fully warmed-up engine where fueling is in its normal operating mode.

Min Run Time (default: 60s)

Discards all samples from the first N seconds of the log. This filters out cold-start enrichment and initial sensor stabilization.

Min Change Amount (default: 0 = disabled)

If a cell's average correction is smaller than this absolute value, it gets zeroed out. Useful for ignoring noise — if you set this to 1.0, any cell recommending less than ±1% change will be left alone. It is applied last, after scaling and smoothing.

Example: Set to 2.0 — a cell with a correction of +1.5% becomes 0 (no change). A cell with +3.2% is kept as-is.

How Corrections Work

For each valid log sample, the tool computes:

correction = ((1 + CL_trim_avg / 100) × (lambda_actual / lambda_target) − 1) × 100

≈ lambda error % + closed-loop trim %

  • Positive correction → engine is running lean (lambda above target) or closed loop is adding fuel → VE table needs to be increased (add fuel)
  • Negative correction → engine is running rich or closed loop is removing fuel → VE table needs to be decreased (remove fuel)

Example: target λ 0.865, measured λ 0.850 (1.7% rich) while closed loop is trimming −8%: (0.92 × 0.850 / 0.865 − 1) × 100 = −9.6%. Both signals say the table has too much fuel.

A sample between breakpoints is shared between the surrounding cells in proportion to how close it is — the same interpolation M1 uses to read the table — so a sample halfway between two RPM sites counts half in each. The final correction for each cell is the weighted average of its samples, and its hit count is the total weight.

Important: The closed-loop trim (CL_trim) is included in the calculation. This accounts for corrections the ECU has already made, giving you the total error including what closed-loop is compensating for.

Scaling Factor

Default: 100% (apply the full recommended correction).

Set this lower to apply only a fraction of the correction. This is a common conservative tuning practice — apply 50–75% per iteration to avoid overshooting, especially on a first pass or when you're unsure about data quality.

Example: A cell shows +6% correction. With scaling at 75%, the applied correction becomes +4.5%.

Tip: Use 100% when you have high-quality data (lots of hits, low std dev, steady-state driving). Use 50–75% on early iterations or when the std dev is high.

Outlier Filtering

Default: 0 (disabled).

When enabled, the tool performs a two-pass analysis:

  1. First pass: Bins all samples and computes the mean and standard deviation for each cell.
  2. Second pass: Discards any sample whose correction is more than Nσ (standard deviations) from its cell's mean, then recomputes the final averages.

This removes transient spikes (tip-in/tip-out, sensor glitches, momentary misfires) that would otherwise skew the average.

Example: Set to 2.0 — a cell with mean correction +3% and std dev 1.5% will discard any sample with correction outside the range [-0%, +6%].

Recommended values: 2.0–3.0σ. Lower values are more aggressive (discard more data). Start with 2.5 if unsure.

TPS Rate Filter

Default: 0 (disabled).

Discards samples where the throttle position is changing faster than the specified rate (%/second). During rapid throttle changes, lambda readings lag reality due to sensor response time and fuel transport delay. Filtering these out gives you only steady-state data where the lambda reading accurately reflects the VE table's contribution.

Example: Set to 50 — any sample where TPS is changing faster than 50%/second is discarded.

Recommended values: 30–100 %/s depending on how aggressive your driving style is. Lower values are stricter (more steady-state only). For track data with lots of transients, try 50. For street driving, 100 may be sufficient.
Note: This filter requires the "Throttle Position" channel in your log. If it's not present, the filter is automatically disabled and a warning is shown.

Correction Smoothing

Default: 0 (disabled).

Applies a Gaussian spatial smoothing filter to the correction grid after scaling and before the Min Change Amount cut-off. Each cell's correction is blended with its neighbors using distance-weighted averaging. This produces a smoother correction map that avoids abrupt cell-to-cell jumps.

The value controls the Gaussian sigma (blur radius):

  • 0 — disabled (no smoothing)
  • 0.5–1.5 — light smoothing, reduces noise while preserving local detail
  • 2–3 — moderate smoothing, good for noisy data
  • 4+ — heavy smoothing, flattens most local variation

How it works: For each cell above the hit threshold, the tool computes a weighted average of that cell and its neighbors (within a radius of ~2× the sigma value). Neighbors that are below the hit threshold are excluded — they don't contribute to or receive smoothing.

When to use: Smoothing is most useful when your Std Dev view shows moderate-to-high variance across many cells, or when the correction map has isolated spikes that look like noise rather than real fueling errors. Start with 1.0 and increase if the map still looks noisy.
Caution: Over-smoothing can mask real cell-to-cell differences in VE (e.g., around cam changeover points or resonance effects). If your engine has known sharp transitions in the VE map, keep smoothing low or disabled in those regions.

Overrun, Fuel Cut and Implausible Lambda

Always on. When the log contains Engine Overrun State or Fuel Output Cut Count, samples during overrun or a fuel cut — and for 1 second afterwards, while the sensor still reads the cut — are skipped. Any sample whose measured lambda is outside 0.6–1.4 is also skipped: those are free-air, fuel-cut or sensor readings, not combustion, and a single one can swing a cell by tens of percent. Both counts appear in the results summary.

Steady-State Window

Default: 300 ms (0 = disabled).

Uses only samples where, over the preceding window, MAP stayed within 10 kPa and throttle within 10%. During faster MAP or throttle changes the mixture is set by transient (wall-wetting) fuelling, which belongs to the Transient Fuel Analyzer, not the VE table. Engine speed is not limited: a full-throttle pull sweeps RPM quickly but fuels steadily.

Lambda Delay

Default: From the tune (fixed: 300 ms).

Exhaust takes time to reach the sensor and the sensor takes time to respond, so the lambda logged at a moment reflects fuelling earlier. Each sample is paired with the lambda reading its delay later, and is used only if MAP and throttle stay steady from the steady-state window before it until that reading, with no fuel cut in between.

From the tune uses the tune's Fuel Closed Loop Period — the time from a fuel change to the lambda reading it, by exhaust mass flow (MoTeC sets it from aim step tests; ~2 s at low flow to ~0.5 s at high flow as a start) — at each sample's exhaust mass flow: the logged Exhaust Mass Flow, else Engine Load × cylinders × rpm ÷ 120 plus the fuel. The delay is longest at idle and light cruise (about 0.8–1 s on the LT4 tune) and short under load. The result line shows the delays used. Samples without Engine Load in the log fall back to the fixed value.

If the tune's Period is a guess rather than measured, the delay is only as good as that guess — a closed-loop step test settles it.

Decel/Overrun Filter

Default: Enabled.

Automatically rejects samples captured during deceleration and engine overrun conditions. During decel, the throttle is closed, MAP is falling rapidly, and the lambda reading is unreliable due to:

  • Exhaust reversion pulling fresh air past the wideband sensor
  • Fuel cut (if active) causing unburned O2 to reach the sensor
  • Residual fuel film evaporating without combustion

The filter detects decel by combining two conditions:

  • TPS < 1% AND MAP falling faster than 50 kPa/s — active deceleration with closed throttle
  • TPS < 0.5% AND MAP < 40 kPa — closed-throttle coasting at high vacuum

This preserves legitimate light-cruise data (where TPS is 2-5% even at low MAP) while rejecting the overrun samples that would otherwise skew low-MAP cells lean.

Why this matters: Without this filter, decel samples accumulate in the 20-40 kPa cells with artificially lean lambda readings. The tool then recommends reducing VE in those cells, which makes the engine too lean during actual light-cruise driving at those MAP values.
Requires: "Throttle Position" channel in your log. If not present, the filter is automatically disabled and a warning is shown. In that case, use the Min MAP filter as a fallback.

Min MAP for Corrections

Default: 0 (disabled).

A hard cutoff that excludes all samples below the specified MAP value from the correction calculation. Cells below this MAP will show as empty (no correction) regardless of how many samples they have.

Example: Set to 25 — all cells at 25 kPa and below will be excluded. Useful if you know your engine never operates at those MAP values under normal driving conditions.

When to use: As a safety net in addition to the decel filter, or as a standalone solution if the decel filter can't be used (no TPS channel). Typical values: 20-30 kPa for naturally aspirated engines.
Trade-off: Unlike the decel filter, this blanks out ALL data below the threshold — including legitimate light-cruise data. If you cruise at 25 kPa in top gear, setting this to 30 would prevent those cells from being corrected. Prefer the decel filter when possible.

Display Views

After processing, four table views are available via the toggle buttons:

Correction %

The primary output. Shows how much to adjust each VE cell. Green = add fuel, red = remove fuel, grey = insufficient data.

New VE Values

Shows the complete recommended VE table with corrections already applied. Cells that changed are highlighted; unchanged cells are greyed out. Useful for a quick visual sanity check that the resulting table looks smooth.

Hit Counts

Shows how many valid samples landed in each cell. Green cells exceeded the hit threshold and contributed to corrections. This helps you identify areas of the map with insufficient data coverage — you may need more driving time at those RPM/MAP combinations.

Std Dev

Shows the standard deviation of corrections within each cell. This indicates data quality and confidence:

  • Green (≤1.0) — tight clustering, high confidence in the correction
  • Yellow (≤3.0) — moderate spread, correction is reasonable but not perfect
  • Red (>3.0) — high variance, treat this correction with skepticism. Consider enabling the outlier filter or gathering more data.

Checking a Cell Against the Log

Click any cell in the results table to open the Log Viewer below it. It shows the log with the samples that count towards that cell highlighted, and shaded bands where each filter left data out, so you can see what a correction is based on. Previous / Next step through the stretches of samples in the cell.

3D Surface Plot

A 3D wireframe surface visualization appears below the table. It renders the selected data (corrections, new VE values, or std dev) as a color-coded surface over the RPM × MAP grid.

Controls

  • Drag — rotate the view (left-right = yaw, up-down = pitch)
  • Scroll wheel — zoom in/out
  • Data dropdown — switch between Correction %, New VE Values, or Std Dev
  • Reset View — return to the default viewing angle
Tip: The 3D view is especially useful for spotting discontinuities or spikes in the correction map that might indicate bad data in a specific cell. A smooth surface suggests consistent, trustworthy corrections.

Copy to Clipboard

The "Copy Table to Clipboard" button copies whichever table view is currently displayed as tab-separated values. This pastes cleanly into:

  • Microsoft Excel
  • Google Sheets
  • LibreOffice Calc
  • Any text editor (as a tab-delimited table)

The button briefly shows "Copied!" as confirmation. Switch between views (Correction %, New VE Values, etc.) and copy whichever one you need.

Output Files

VE_Difference.csv

A simple grid showing the correction percentage for each cell. Cells below the hit threshold are empty. This is useful for record-keeping or importing into a spreadsheet for further analysis.

VE_New_Values.csv

A complete M1 v2 format VE table with corrections applied. This file can be imported directly back into MoTeC M1 Tune to replace your current VE table. Cells that didn't meet the hit threshold retain their original values unchanged.

Recommended Workflow

  1. Gather data: Drive the car through as many RPM/MAP combinations as possible. Steady-state cruising, part-throttle acceleration, and highway driving all contribute. Aim for at least 5–10 minutes of varied driving after warmup.
  2. First pass (conservative):
    • Set scaling factor to 75%
    • Set outlier filter to 2.5σ
    • Set TPS rate to 50 %/s
    • Set min change to 1.0%
  3. Review results: Check the Std Dev view. If many cells show red (>3σ), your data may have too many transients — try lowering the TPS rate filter or gathering more steady-state data.
  4. Apply and re-log: Import the new VE table, drive again, and re-analyze. Each iteration should show smaller corrections as the table converges.
  5. Final pass (full correction): Once corrections are consistently small (±1–2%), switch to 100% scaling and lower the min change threshold to capture the remaining fine adjustments.
  6. Convergence: You're done when the correction table shows mostly zeros or very small values across the operating range you care about.
Pro tip: Keep your VE_Difference.csv files from each iteration. Comparing them shows how quickly the table is converging and whether any cells are oscillating (which might indicate a sensor issue or a cell that spans too wide an operating range).
